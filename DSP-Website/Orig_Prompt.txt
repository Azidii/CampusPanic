# PROJECT CONTEXT
CampusPanic is a campus emergency alert system. ESP32 nodes are installed in rooms, each with a fixed building and room ID. Each node has a MAX9814 microphone running a TinyML CNN (flags suspected gunshots) and a three-button panel (medical, fire, panic). A flagged audio event activates a laptop webcam, a firearm detector verifies it, and the result is sent to the security station (this website) as an alert.

Alert packet fields (this is the data contract):
- building, room, nodeId
- emergencyType: "gunshot" | "medical" | "fire" | "panic"
- threatStatus: "verified_threat" | "unverified_audio_trigger" | "manual_alert"
- priority (verified_threat highest; manual alerts always transmitted; unverified lower)
- sequenceNumber, timestamp, checksum
- optional image (captured webcam frame)
- audioConfidence, firearmConfidence (optional)

Delivery behavior: the server validates the checksum, returns an ACK to the sender, stores the alert, and queues it by priority. Duplicates (same nodeId + sequenceNumber) must be ignored but still ACKed. The UI must state plainly when a firearm was NOT verified.

# ROLES AND FEATURES

## Admin
Admins have every User feature plus user management:
1. Add user (name, email, password, role, assigned building optional)
2. View users (searchable, filterable table)
3. Edit user (details, role, active/disabled status, password reset)
4. Delete user (with confirmation; an admin cannot delete themselves)

## User
1. Dashboard: live alert feed sorted by priority then time, counts per emergency type, node online/offline status, acknowledge/resolve actions, latest alert highlighted, alert sound for verified threats
2. Cam View: view of the webcam/verification feed and captured image for a selected node or alert
3. All Cams (CCTV-style main server view): grid of all connected camera sources (laptops/phones streaming via WebRTC or periodic snapshots), with online/offline status, label (building/room), click to enlarge
4. Map View: campus map showing all nodes as markers (building, room, status)
5. Active Nodes Map: same map showing only activated nodes, color-coded by reason (gunshot verified / gunshot unverified / medical / fire / panic), with a popup showing reason, time, threat status, and image; pulsing animation for active ones
6. Profile: view/edit own name, email, change password
7. Settings: theme (light/dark), alert sound on/off, notification preferences
8. Sign out

# TECH REQUIREMENTS
- Backend: Node.js, Express, Mongoose, JWT auth (httpOnly cookie or Bearer token), bcrypt, role-based middleware (`admin`, `user`), express-validator, helmet, cors, rate limiting
- Realtime: Socket.IO for pushing new alerts, node status changes, and camera frames to clients
- Frontend: React (Vite), React Router with protected and admin-only routes, Tailwind CSS, Leaflet (react-leaflet) for maps with a configurable campus center and a custom floor/campus image overlay option
- Camera: WebRTC or simple frame-upload streaming to the server, with a clearly documented approach; fall back to periodic JPEG snapshots if WebRTC is too complex
- Images: store alert images on disk (multer) or GridFS, reference by URL

# DATA MODELS (Mongoose)
- User: name, email (unique), passwordHash, role, isActive, assignedBuilding, createdAt
- Node: nodeId (unique), building, room, lat, lng, status (online/offline/active), lastSeen, cameraId
- Alert: nodeId, building, room, emergencyType, threatStatus, priority, sequenceNumber, timestamp, checksum, imageUrl, audioConfidence, firearmConfidence, status (new/acknowledged/resolved), acknowledgedBy, createdAt. Unique index on (nodeId, sequenceNumber)
- Camera: cameraId, label, nodeId, online, lastFrameAt

# API ENDPOINTS
- Auth: POST /api/auth/login, POST /api/auth/logout, GET /api/auth/me
- Users (admin only): GET/POST /api/users, PUT/DELETE /api/users/:id
- Profile: PUT /api/profile, PUT /api/profile/password
- Nodes: GET /api/nodes, POST/PUT/DELETE (admin only)
- Alerts: GET /api/alerts (filters: status, type, building), PATCH /api/alerts/:id (acknowledge/resolve)
- Ingest from ESP32/gateway: POST /api/alerts/ingest with a device API key header (separate from user auth). Validate fields and checksum, dedupe, store, emit via Socket.IO, and respond with `{ ack: true, sequenceNumber }`
- Cameras: GET /api/cameras, plus upload/stream endpoint for the laptop gateway

- Hash passwords, validate and sanitize all input, never expose passwordHash
- Device ingest uses an API key; user routes use JWT
- No continuous video storage: store only triggered alert images; add a configurable retention period that auto-deletes old images
